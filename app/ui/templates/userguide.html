Training, Validation & Test Data

A machine learning model learns numerical patterns based on past data, similar to an supply chain learning the trends of a customer. An expert might recall part numbers that behave consistently, or make assessments based on seasonality. A model develops a complex formula based on historical data that it is given; the formula changes if the input data changes - the input set is called the "training set." Once a model is trained, it doesn't change until you train it again.

Before using the model to predict future ordering, it's important to characterize it's ability to do so. Order data from the training set can't be used to evaluate the performance - it's akin to using a study guide question on the final exam. The model has an unfair advantage.

  • Training data - the historical order weeks the model studies to learn its patterns. You choose this range on the Train page.
  • Validation data (also called a "holdout" set) - a handful of the most recent weeks inside that same historical range, deliberately hidden from the model while it learns. Right after training, you can check how well the model would have predicted those hidden weeks - like a practice quiz using questions you already have the answer key for. You choose how many weeks to hold back with Validation Weeks on the Train page, and review the results on Evaluate ("Validation set").
  • Test data - real order data the model has never seen. This might be the most recent data, or it might be data that wasn't included in the training data - for example, training on all of 2024-2025, even though the first weeks of 2026 aren't recent, they are new to the model.
  • Prediction data - real order data the model has never seen, because they didn't exist yet when you trained it. This is the closest thing to grading the actual forecast, but it can't happen instantly: it takes time for those orders to be placed and for real consumption to be posted for them.

🗓️ The week you train a model
  • Only training and validation data exist yet - nothing else has happened.
  • The validation score is your only signal of quality, and it's a bit optimistic: those weeks sit right next to the training data and share its season and trends.
  • The Predict page will happily generate forecasts for future weeks, but there's no way yet to know if those specific forecasts are correct.
  • Good for: sanity-checking a new model and comparing it to earlier ones before you rely on it.
📅 Next week (or later)
  • Real consumption has now posted for some of the weeks the model predicted "blind."
  • Go to Evaluate → Test On → Recent week to score the model against this brand-new, genuinely unseen data - a real test, not a rehearsal.
  • If the recent-week score is close to the validation score, trust the model.
  • If it's noticeably worse, the validation score was too optimistic - likely time to load the new weeks' data and retrain.

Automated workflow

The fundamental workflow for the tool does not involve any manual steps once it is set up:

  1. The SCMDW folder updates with new data on Tuesdays. This includes two files per plant: ictrans and custdemand. ictrans gives all transactions recorded within the past 8 days, while custdemand gives the customer waterfall.
  2. The routine in app/routine.py (a Python script, not a bash script) looks in that folder for files named [plantkey]_ictrans.txt and [plantkey]_custdemand.txt, where the plant key comes from the plant_key dictionary in app/prefixe.py (e.g. Arlington → AT_ictrans.txt, AT_custdemand.txt).
  3. For each run, the routine:
    1. Writes an error report into reports/<year>wk<week>/.
    2. Loads whichever of the two files it finds into the plant's database, then moves each file into data/<plant>/<data type>/<year>wk<week>.txt as an archive. If neither file is found, it stops here and logs the run as no_new_data.
    3. Retrains the model (one week held out), using the configuration of the best previously saved model for that plant.
    4. Saves the model as models/saved_models/<plantkey>_<year>wk<week>_<timestamp>.pkl.
    5. Makes predictions 4 weeks ahead and saves them to reports/<year>wk<week>/predictions_<model name>.xlsx.
  4. Every step is recorded as passed/failed/skipped in logs/routine_runs/, which the Run History page displays.

To run it by hand from a Command Prompt in the project folder (with the virtual environment activated; see Step 5 of "Moving devices" in the README): 

python -m app.routine

This takes no arguments. It runs the routine once for every plant in plant_key, one after another, reading from the default incoming folder (SCMDW on the Desktop of the Windows user running it; see 'incoming' in dirs in app/prefixe.py) and archiving into data/<Plant>/. Plants whose files aren't there are logged as no_new_data. If one plant's run fails, the plants after it are not run that time.

Note: use python -m app.routine, not python app\routine.py; the second form can't find the app package.

When started from the Run History page instead, the incoming folder has to be inside the default incoming folder (SCMDW on the user's Desktop) or the project's data/ folder, because the app only lets you browse there.

Manual reporting

The reporting module exists to provide feedback on the tool itself and model performance. Reports are run from the Reports page; pick a plant, an optional week range, an optional part-number prefix, and optionally a folder to save the output to. The following operations are supported:

  • Order accuracy / ordering history report (error_report): compares historic customer forecasts (waterfall) against what was actually ordered, broken out by how far ahead the forecast was made (lookahead). Use "max lookahead" to limit how far out to look.
  • Data coverage report (coverage_report): shows which weeks and parts are present in each table, to spot missing weeks.
  • Model performance report (holdout_report, on the Evaluate page): for a given trained model and test dataset, provides diagnostics about past model performance.
Filling missing week data

Based on the data mosaic shown on the Load page, it may be evident that there is missing info. To manually load data outside of the automation pipeline:

  1. Get the file(s) for the missing week(s).
  2. On the Load page, select the plant under "Plant Source", choose the "Data Type", and upload the file(s). You can select and load files individually OR just highlight all files at once.
  3. Re-check the coverage heatmap on the Load page to confirm the gap is filled.
  4. Retrain (Retrain page, or the next automation run) so the model sees the new data.

Note that because the week is the smallest unit of time, a week that is only partly loaded is treated as incomplete.

Manual data loading can be performed on the old .prn style, OR the new .txt, pipe-delimited data warehouse format. See "Ingestion formats" under Developer reference in README.html (project folder) for the difference between these formats.

🚫 Excluding Weeks from Training

Some weeks shouldn't be learned from: a plant shutdown, or a one-time event that won't happen again. The Train page lets you leave those weeks out. Excluded weeks are dropped from both training and validation scoring, so they neither teach the model nor count for or against its score. They are still treated as real history, though: their numbers still feed the "recent trend" features of the weeks that follow them.

Excluding is for correct data that isn't typical demand. If a week's numbers are wrong (for example, a data entry mistake), don't just exclude it: fix the data. Get a corrected file for that week and load it on the Load page with Overwrite ticked, which replaces the week in the database. Excluding a wrong week isn't enough, because its numbers still feed the trend features of the weeks after it, and every report and later model still sees them.
Exclude Consumption Weeks Order weeks whose actual consumption is correct but unrepresentative (wrong numbers should be reloaded with Overwrite instead; see above). Every prediction made about that order week is dropped.
Exclude Waterfall Weeks Snapshot (release) weeks whose plan doesn't reflect normal ordering. Every prediction made from that week's waterfall is dropped, whichever order weeks it covered.
Format Comma-separated weeks or ranges: 2025-W52, 2026-W01..2026-W03, or the shorthand 2026-W05..W07. Put a part number and a colon in front to exclude that part only, e.g. 1234-567:2026-W10. A typo stops training with a message showing the token it couldn't read.
Choose weeks… Opens a calendar of every week with data, one grid for waterfall snapshots and one for consumption order weeks. Darker squares have more parts. Click a week to switch it between kept and excluded, drag across several, or click a year to switch the whole row. Keep all weeks clears the current plant's picks.
Applies to Picks are saved per plant. Weeks picked under All plants apply to every plant and show striped in each plant's view; to change one, switch back to All plants. A plant's exclusions are its own picks plus the All plants picks.
  • Saved picks are remembered between sessions. They fill the two text fields whenever you open Train or change the plant. Part-specific entries you typed yourself are kept.
  • Each model saves the exact exclusions it was trained with. Retrain from a past model refills the fields with that model's exclusions instead of your saved picks.
  • Exclusions only apply to models trained from the Train page. Automation and optimization runs on Run History train on every week.
🛠️ Run History

Run History starts the two automated jobs and keeps a record of every time either one ran, whether from this page or from the command line. Both run in the background, so you can leave the page and come back. Only one job of each kind can run per plant at a time.

Run Automation The weekly routine (routine.py). For the chosen plant it:
  1. writes an error report covering recent weeks;
  2. loads any new consumption and waterfall extracts found in the Incoming folder, then moves each loaded file to the plant's archive;
  3. trains a new model on all weeks, holding out the last week for validation and reusing the settings of whichever earlier model for this plant scored best;
  4. saves the model, predicts the next 4 weeks, and saves those predictions as a spreadsheet in that week's reports folder.
If no new files are found, it stops after step 2 and is marked No new data. Use Browse… to pick a different incoming folder.
Optimize hyperparameters Searches for better model settings (optimize.py). It tries the plant's current best settings plus random alternatives, for as many Trials as you choose. Each trial is scored at 3 points in time, 4 weeks apart, because one validation split is too noisy to rank settings fairly. If any trial beats the current settings, it is saved as a model, and the next automation run will use those settings automatically. Every trial's score is also saved as a CSV in the reports folder. More trials search more widely, but each one adds minutes.
Run cards One card per run, newest first, showing the plant, which job ran, when it started, and how long it took. Each step is a circle: ✓ succeeded, ✕ failed, – skipped (for example, no file of that type in the incoming folder). Hover a step for its message, or open Step details for the full table, including error text when a step failed. While a job is running, the page refreshes itself every 10 seconds.
Status Success, Failed, No new data, In progress, or Interrupted. Interrupted means the job stopped without recording why, usually because the app was restarted mid-run, or it hasn't reported anything for 2 hours. It's safe to start the job again.
🔤 Key Terms
Naive baseline The "naive model" is assuming the waterfall prediction is correct;
Lookahead How many weeks in advance a prediction was made relative to the order week it's about. Predictions made further ahead are naturally less certain, which is why Reports and Evaluate can break accuracy down by lookahead.
R² (R-squared) A "fit quality" score between roughly 0 and 1, where 1 is a perfect fit. Higher than the naive baseline's R² is the bar to clear. Anything outside of the range of 0/1 points to an unstable model. A score of 0.1 is a bad model, 0.6 is ok, 0.9 is excellent, and 9.284 is very very bad.
MAE (Mean Absolute Error) The average size of the model's miss, in the same units as the order quantity. Easiest metric to read literally - lower is better.
MSE (Mean Squared Error) Like MAE, but squares each miss first - so a few big misses move this number a lot more than many small ones. Lower is better.
❓ FAQ
Why can't I test a freshly trained model against this week's predictions right away?
Grading a prediction requires real consumption to actually be posted for that order week, and that only happens once time - and the normal lag between ordering and consumption - has passed. Until then, the validation score from historical weeks is the best signal available.
Why does my model do so much worse when I expand the lookahead horizon?
Given that the original data does not expand past a 24 week horizon, expanding predictions past these dates results in much less reliability.
My model's validation score looks great - can I trust it right away?
It's a good early signal, but validation weeks are drawn from the same historical stretch as training, so they tend to share the same seasonality and trends the model already learned. Confirm with a Recent week test on the Evaluate page once real data is available - that's the true out-of-sample check.
How often should I retrain a model?
There's no fixed schedule. Good triggers: recent-week test accuracy starts drifting away from the validation score, a new batch of weeks' consumption has been loaded (check the Data Coverage heatmap on Load), or you're heading into a period with unusual demand.
I loaded a consumption file, but its last week isn't showing on the Data Coverage heatmap. Why?
A consumption week only appears once it is finished. A week counts as finished when it has shipments on all seven days, or when a later week has been loaded. Days with no shipments (Sundays, holidays) count as zero once a later week arrives. The last week in a file is held back until it has all seven days or until the next file is loaded. This way, a file that ends mid-week doesn't record a partial total. Only real part shipments (ISS-SO) are counted, so a shutdown week with only accounting entries shows as empty.
Training failed with "Target 'Volume Error' needs part cost data." What do I do?
The Volume Error target multiplies each part's error by its cost, so it only works for a plant whose Cost files have been loaded. Hermosillo currently has no cost data. Either:
  • Change Target to Error (order − pred qty) (the default) or Raw and train again. Neither uses cost, and both work for every plant.
  • Or load the plant's Cost files on the Load page, then train again with Volume Error.
If cost is loaded for only some parts, Volume Error trains, but it skips every part that has no cost.
Training failed with "Size threshold … leaves Model A (or B) with no training rows." What do I do?
With Split model on, Model A learns from rows whose predicted quantity is above the Size threshold and Model B from rows at or below it. If the threshold is above every predicted quantity in your data, Model A gets nothing to learn from. If it is below all of them, Model B gets nothing. This is easy to hit when training on a short date range or on a smaller plant like Hermosillo. The error message shows the predicted-quantity range in your data. Either:
  • Set the Size threshold to a value inside that range (the default of 1 usually works), or
  • Turn off Split model and train a single model.
Training failed with "No training data found for the specified date range." What do I do?
No week in your Earliest/Latest order date range has both waterfall predictions and posted consumption for this plant. Check the plant's weeks on the Data Coverage heatmap on the Load page, then pick a range inside them, or leave both dates blank to use everything. This often happens after filling the form with Retrain model from another plant's model, since that copies the other plant's dates, and plants don't all cover the same weeks.
I tried to upload a file and the upload failed, saying "database is locked." What do I do?
Close the tool and try again. Closing the browser tab isn't enough: also close the Python terminal window the tool runs in, then start the tool again. This usually happens when an earlier load crashed partway through and left the plant's database open.
Can I go to a different page while data is loading, a model is training, or an optimization is running? Will it mess up the operation?
Switching pages won't stop or damage the job, because the work runs in the Python terminal window, not in the browser tab. What you lose by leaving depends on the job:
  • Loading data: the load keeps going, but the list of loaded and skipped files won't be shown when it finishes. When you come back, check the Data Coverage heatmap on the Load page to confirm the new weeks are there. Wait a little before loading more files, so the two loads don't overlap.
  • Training: the model still trains and is saved, but the progress bar and results don't come back when you return to the Train page. The new model will appear in the model lists once it's done.
  • Automation and optimization (Run History): these run in the background by design. Leave and return whenever you like; the run card shows the progress.
In every case, don't close the Python terminal window until the job has finished. That stops the job partway through.
