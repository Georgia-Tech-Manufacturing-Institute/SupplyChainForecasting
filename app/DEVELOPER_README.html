Developer README

How raw plant extracts become the weekly forecast-vs-actual data the models train on. The guide covers the input file formats, the per-plant SQLite schema, the shape of parsed rows and where data is filtered along the way.

Code lives in app/core/: parser.py (extract parsing), processor.py (fixed-width reports), loader.py (SQLite), common.py (week indices).

1. Model assumptions

The week is the smallest unit of time. A week of actuals counts as complete only when every one of its days is present. Until then it is held back and is not available to train on.

Weeks are ISO weeks and are stored as one integer index, year * 52 + week (week_to_idx / make_week_idx in common.py). The ISO year is used rather than the calendar year so that a date such as 12/31 stays in the same week as the rest of its week.

  • orderidx: the week a quantity is demanded or consumed.
  • predidx: the week a forecast was released.

The prediction dataset holds one row per unique (part, orderidx, predidx) triple. Each part therefore has one forecast quantity per order week, per release, per plant.

2. Ingestion formats

Each plant has a source-system key (AT, CU3, 485, …). Weekly extracts are named {key}_custdemand.txt and {key}_ictrans.txt. Older history arrives as fixed-width YYYYwkWW.prn reports.

Customer demand: {key}_custdemand.txt

Pipe-delimited, with fixed header columns followed by one column per forecast week:

Ship-From|Description|Order|Line|Customer|Customer Sort|Ship-To|Name|Week#|Rel Date|SO|Ln|ShipTo|Customer Part|Part|PCR|00/00/00|...

Each MM/DD/YY column is an order week, and its cell is the quantity forecast for that week in the release dated Rel Date. custDemandParse melts these columns into rows (orderdate, predqty).

AT00|IAC Group - Arlington|GMA139|8|01008607|DAKKOTA INTEGRATED SYSTEMS|01009399|INTIER-KELLER ROAD WAREHOUSE|32|08/03/26|GMA139|8|01009399|84824532|84824532|6|0|0|0|1|0|0|...
AT00|IAC Group - Arlington|GMA139|29|01008607|DAKKOTA INTEGRATED SYSTEMS|01009399|INTIER-KELLER ROAD WAREHOUSE|32|08/03/26|GMA139|29|01009399|84824550|84824550|26|0|0|1|0|1|1|...

Transactions: {key}_ictrans.txt

Pipe-delimited inventory transactions. Only ISS-SO rows (issues to sales orders) are kept as consumption. Other types, such as ISS-WO below, are dropped.

AT00|L0413592AA02600|07/27/26|41464722|ISS-WO|-10|EA|-10|WIP|524

Legacy .prn reports: YYYYwkWW.prn

Fixed-width reports read by stateParse / parse_fixed_width in processor.py. The examples are in that file.

  • Diamond (waterfall) report: waterfallParse. It carries the same fields as the demand extract and goes through the same waterfallProcess. A file is skipped if loaded_files already has it.
  • Transactions By Item Summary: process_consumption_prn → consumpParse. These are already weekly totals and carry no transaction dates, so the week comes from the YYYYwkWW filename. Rows go straight into consumption_agg and bypass the landing table. Each row is part, orderidx, orderqty, with the absolute value of Quantity1 and thousands separators stripped.

Cost / price lists: Cost/*

A fixed-width report in the diamond-report style. It has a header block (program name, report title, Date:/Page:/Time: lines), a column-header line, a ---- ruler line, then one row per price-list line. stateParse skips everything before the first ruler and takes column widths from the ruler's dash groups. The ruler must have exactly one dash group per column, in this order:

Line LineDesc List Name Item Number UM ItemDesc PO UM Start Expire T Cur MinQty1 Amt1 MinQty2 Amt2 MinQty3 Amt3 MinQty4 Amt4 MinQty5 Amt5 BaseCurr TotalCost Remarks

Columns are matched by position, not by header text. The names above are the ones costPrep assigns. For example:

xxpprp.p                                 Price List Report                                     Date: 04/16/26
Page:    1                               Arlington                                             Time: 13:16:05

Line LineDesc List     Name     Item Number        UM ItemDesc       PO       UM Start    Expire   T Cur MinQty1 Amt1    ...
---- -------- -------- -------- ------------------ -- -------------- -------- -- -------- -------- - --- ------- ------- ...
1    ...      ...      ...      84824532           EA ...            ...      EA 01/05/26 12/31/26 P USD     1.0   12.50 ...

After costPrep, three columns remain, one row per part:

columnsource fieldnotes
partItem NumberMust match the Part values in the demand data.
startStartEffective date, MM/DD/YY. Only the latest Start per part is kept.
amountAmt1Unit cost at the first quantity break, parsed as a float.

Rows whose second UM column is --, whose Amt1 is blank or whose Item Number is the literal header text are dropped. This removes repeated page headers and rulers.

3. Plant database schema

Each plant gets its own SQLite file at data/processed/{plant}.db, created by sql_setup() in app/core/loader.py. All plants share the six tables below.

No foreign keys

Tables relate only through part and the week indices orderidx and predidx. SQLite enforces none of these links, so a part can exist in one table and be missing from another. filter_disjoint() trims those parts at dataset time.

loaded_files is per week

Its key is (data_type, week_idx), not the filename. A waterfall extract writes one row per release week it covers, and a consumption load writes one per closed order week. The loaders read it back to skip weeks that are already closed. cost loads are not logged.

Schema version

SCHEMA_VERSION = 1 moved the old pre-aggregated consumption into consumption_agg. The migrate_schema() call in sql_setup() is currently commented out, so a v0 database opened now keeps its old consumption table.

4. Parsed row formats

Both waterfall sources (the demand extract and the legacy diamond report) pass through waterfallProcess in parser.py. That function lower-cases and normalises column names, computes the week indices and keeps only the columns in WATERFALL_KEEP. These are the columns of the waterfall landing table:

columnmeaning
partPart number, cast to str and stripped.
reldateRelease date of the forecast.
shiptoShip-to location. One part can be forecast separately for several destinations.
pcrPCR value from the source, as an integer.
predqtyForecast quantity for the order week, from the melted date columns. Stored as qty in the landing table.
predidxWeek index of the release: ISO year/week of reldate.
orderidxWeek index of the order: ISO year/week of orderdate.

Week#, SO, Ln, CustomerPart, orderdate and the intermediate lookahead/year/week columns are dropped once the indices exist. The result is deduplicated. Landing rows are unique on (part, orderidx, reldate, shipto). waterfall_agg then sums across ship-tos to the (part, orderidx, predidx) triple the models use.

The other parsers produce simpler shapes from the same fixed-width reader. The consumption shapes are in Transactions and Legacy .prn reports, and the cost shape is in Cost / price lists.

5. Filtering

Data is filtered at several points, each for a different reason. Rows that are clearly not useful (wrong transaction type, malformed part numbers, page furniture from reports) are dropped before SQL ingestion. Everything else is kept at full extent in the database, because features such as rolling values need the full history. Narrowing to a modelling set happens later, at dataset time.
