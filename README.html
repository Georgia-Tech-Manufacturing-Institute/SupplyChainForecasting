Advanced user flows

Before you start

This is stuff that should be left to the professionals (i.e. someone who knows how to roll back a version, at least; see Rolling back to an older version). There are a lot of opportunities for things to go wrong, so make a copy of the data/ and models/ folders before starting.

Change folder locations

Every folder the tool reads or writes is set in one place: the dirs table near the top of app/prefixe.py. Change a line there to move that folder, e.g. to write reports to a shared drive or keep models somewhere else. No other code needs to change, and the scheduled task doesn't need to change either.

EntryDefaultWhat lives there
'incoming'~/Desktop/SCMDWWhere the weekly automation looks for new extracts.
'reports'reports/Weekly error reports and predictions (<year>wk<week>/ subfolders), and spreadsheets saved from the Predict page.
'saved_models'models/saved_models/Every trained model (.pkl).
'run_logs'logs/routine_runs/Run history shown on the Run History page.
'data'data/Raw weekly files (data/<Plant>/), saved training exclusions (training_exclusions.json), and by default the processed databases.
'processed'data/processed/One SQLite database per plant. Follows 'data' unless you set it separately.

The table is in two parts. Change the entry where it's defined, and keep the format: a Path(...), with r'...' around Windows paths so the backslashes are read literally. For example, to send reports and models to a network share:

dirs = {
    'app': APP_DIR,
    'data': PROJ_DIR / 'data',
    'reports': Path(r'\\servername\share\Forecast\reports'),
}

dirs.update({
    'processed': dirs['data'] / 'processed',
    'incoming': Path(r'\\servername\share\SCDW'),
    'saved_models': Path(r'\\servername\share\Forecast\saved_models'),
    'run_logs': PROJ_DIR / 'logs' / 'routine_runs',
})

Then:

  1. Move what's already there. Copy the old folder's contents into the new one before restarting. The tool doesn't look in the old place any more, so a new 'saved_models' folder with nothing in it means the automation starts again from default settings, and an empty 'processed' folder means no plant data.
  2. Restart the app (close its window and start it again). The paths are read once at start-up.
  3. Test it (see below).

Things to watch for:

  • Use full network paths (\\servername\share\...), not a mapped drive letter like S:\. Scheduled tasks often can't see mapped drive letters (see Step 9).
  • Keep 'processed' on the computer's own disk. SQLite databases on a network share or a OneDrive-synced folder can lock or corrupt. Reports, models and raw files are fine on a share.
  • The account running the app or scheduled task needs write access to every folder except 'incoming', which needs read access, plus permission to move files out of it.
  • Update Backups to copy from the new locations.
  • Docker: leave prefixe.py alone. Inside the container the project sits at /app, so the app uses /app/data, /app/models and /app/reports. To move a folder, change the left side (the host folder) of the matching volumes line in docker-compose.yml, then restart the container. The right side must be the container path the app uses. The current file mounts to /data, /models and /reports, which the app doesn't read. Those need to be /app/data, /app/models and /app/reports before the host folders take effect.

The incoming (automation) folder

Whichever folder you use for 'incoming', it must hold the extracts directly (e.g. AT_ictrans.txt, AT_custdemand.txt), not in subfolders. After loading, each extract is moved to data/<Plant>/<data type>/.

  • Scheduled task / command line: python -m app.routine takes no arguments and always reads 'incoming'.
  • Run History page: you can pick a different folder in the incoming-folder box for a single run, but the page can only browse inside the 'incoming' folder and the 'data' folder. A network share can't be browsed here unless it is one of those two.

To test a new incoming folder: put the week's extracts in it (or wait for the next drop), run the routine once, and check that the Run History page shows the load steps as passed rather than skipped. Don't just look for no_new_data: that only means the files weren't found. For the other folders, check that the next run's report, model or log appears in the new location.

New plant

Needed: historical data in a known form. Form is either the concatenated diamond reports or the automated warehouse format; the latter is preferred.

  1. Register the plant source. Open app/prefixe.py:
    • Add the name of the plant to the _BASE_PLANT_SOURCES list.
    • Double check that there is an existing entry for the plant in plant_key (lowercase name → key). The automation needs this key to find the plant's [key]_ictrans.txt / [key]_custdemand.txt files.
  2. Prepare the raw historical files for the plant, one file per week, named YYYYwkWW.prn or .txt (e.g. 2026wk01.prn), for each data type you have (Waterfall, Consumption, Cost).
  3. On the Load page, select the new plant under "Plant Source", choose the "Data Type", and upload the files (individually or as a folder). Files are copied to data/<plant>/<data type>/ and parsed into that plant's database.
  4. Repeat step 3 for each data type / batch of weeks you need to backfill.
  5. Confirm the load on the Home page's Plant Sources table (weeks/parts counts) or the Load page's coverage heatmap.
  6. Train a first model for the plant on the Retrain page so the automation has a configuration to start from.

Deleting a plant

Given a plant "ExamplePlant", say we want to remove it and all its data. There is currently no UI action for this; it must be done by hand:

  1. Remove raw data: delete the data/ExamplePlant/ directory (the raw .prn/.txt files uploaded via the Load page).
  2. Remove the processed database: delete data/processed/exampleplant.db (note the plant's database file is always named in lowercase, regardless of how the plant name is cased elsewhere).
  3. Remove it from the plant list:
    • If it was added via the Home page's "Add Plant" form, remove its entry from data/custom_plants.json.
    • If it was added by hand, remove it from the _BASE_PLANT_SOURCES list in app/prefixe.py.
  4. Optionally, delete any saved models trained on that plant under models/saved_models/ (check each bundle's plant field, e.g. via the Models page).
  5. Restart the app so the in-memory PLANT_SOURCES list picks up the removal.

Feature development

Model features are elaborated in app/models/features.py. There are 4 types of features: waterfall, consumption, accuracy, and part.

No future information

The BIGGEST concern when adding new features is ENSURING that future information is NOT included. The input to both model training and prediction is a row representing a future order date (orderidx), made on a date (predidx). Each row should contain features (columns) ONLY based on information available up to the prediction date. Incorporating future information will often improve performance, but requires information that isn't actually available for real future projections!

Feature engineering is a tantalizing method of model improvement. However, there are a lot of pitfalls within this dataset in particular.

  • Seeing into the future: This is time series 101, but just to be abundantly clear: features should NEVER use information not available at the time of row creation. This is tricky with these datasets, because when the consumption and prediction data are merged, you can accidentally look into the future if you're not careful.
    • For example: if data is sorted according to orderidx rather than predidx, then a "prior" row might already have been ordered, giving unrealistic insight.
  • Lag ≠ prior week. This is one I have to catch myself doing; because customer demand is not always present for every week, sometimes the "last" value is from many weeks ago. At the time of the last week, the lagging value IS the last known prediction, but it was not forecast in the prior week.
  • Holdout noise: a single holdout split can swing the error more than a good feature does. Compare features over several rolling origins before concluding a feature helps.

Opportunities for new features (performed by an intern or others):

  • Exogenous features:
    • Weather forecasts for plants
    • Gas prices
    • OEM info: production schedules, holiday/shutdown calendars

Moving devices

This section covers moving the Forecast Tool to a new Windows computer (or setting it up on one for the first time). It is written for someone who has never used Git. Follow the steps in order and don't skip any.

What moves how

The code is stored on GitHub at:
https://github.com/Georgia-Tech-Manufacturing-Institute/SupplyChainForecasting

Git (the tool that downloads the code from GitHub) only carries the code. The data, the trained models, the reports, and the run history are deliberately left out of Git (they're large, and the data is company information). Those have to be copied over by hand from the old computer. If you only do the Git part, the app will start but will have no plants' data and no models.

WhatHow it gets to the new computer

Throughout these steps:

  • Command Prompt means the Windows program called "Command Prompt" (not PowerShell). Open it by clicking the Start menu, typing cmd, and pressing Enter. It's a black window where you type commands.
  • When a step says "run", type the command exactly as shown and press Enter. Wait for it to finish (you'll get a new blinking line ending in >) before typing the next one.
  • <like this> means "replace this, including the angle brackets, with your own value".
  • You can paste into Command Prompt with Ctrl+V or a right-click. The Copy button on each command box copies it for you.

1Install Python 3.12

  1. Go to https://www.python.org/downloads/windows/ and download the latest Python 3.12 "Windows installer (64-bit)". The tool was developed on Python 3.12; newer versions may work but haven't been tested.

4Check that requirements.txt came down

requirements.txt lists the Python packages the tool needs, with exact versions. It comes with the code. Check it's there:

5Create the Python environment and install packages

A "virtual environment" is a private copy of Python just for this tool, so its packages don't clash with anything else on the computer.

  3. Install the packages:

Getting updates later

When the code is changed on GitHub, the new computer doesn't update by itself. To get the latest version:

  1. Stop the app (close its window).
  2. Open Command Prompt and run: 
    cd /d C:\ForecastTool\SupplyChainForecasting
.venv\Scripts\activate.bat
git pull
pip install -r requirements.txt
  3. Start the app again.

If the update changed the scikit-learn or joblib version in requirements.txt, retrain the models (Retrain page, or let the next automation run do it). Models saved under the old version may not load.

git pull never touches data/, models/, reports/, or logs/, since Git doesn't track them.

If git pull says Your local changes to the following files would be overwritten, someone edited code on this computer. Don't force it. Stop and contact the maintainer, because those edits will be lost otherwise.

Rolling back to an older version

If an update breaks something:

  1. See the recent versions (press q to exit the list): 
    git log --oneline
    Each line starts with a short code, e.g. 44e41f9 standardize common functions.
  2. Switch to the version you want: 
    git checkout <code>
  3. Restart the app. To go back to the latest version afterwards: 
    git checkout main
git pull

Rolling back the code doesn't roll back the data. If a bad version damaged a database, restore data/processed/<plant>.db from a backup copy.

Backups

Since the data and models aren't in Git, the only copy is on the computer that runs the tool. Two things matter most:

WhatWhy it matters
data/processed/*.db One SQLite database per plant (e.g. arlington.db). This is everything the models train and predict from. It can be rebuilt by reloading every raw file in data/<Plant>/ on the Load page, but that is slow, so keep a copy.
models/saved_models/*.pkl Every saved model version. Each automation run and each save from the Train page adds a new .pkl; nothing deletes old ones. Keep all of them, not only the newest: the automation reuses the settings of whichever saved model for that plant had the lowest validation error, so losing older models can change the settings the next run trains with.

When to back up:

  • Once a week, after the weekly automation has run.
  • Before any of the advanced user flows, before a git pull, and before rolling back.

Close the app first (see Step 0), so no database is being written to while you copy it. Then, from a Command Prompt in the project folder, copy both into a folder named for the week, e.g. 2026wk41, on a USB drive or shared drive:

robocopy data\processed "<backup folder>\<year>wk<week>\data\processed" *.db
robocopy models\saved_models "<backup folder>\<year>wk<week>\models\saved_models" *.pkl

A dated folder per week keeps older database versions, so you can go back to a database from before a bad load. Delete old week folders when space runs short, but keep at least the last few.

Models only load with the scikit-learn and joblib versions in requirements.txt (see Step 4). To restore: close the app, copy the .db files back into data\processed and the .pkl files back into models\saved_models, then start the app again.

Developer reference

How raw plant extracts become the weekly forecast-vs-actual data the models train on: the input file formats, the per-plant SQLite schema, the shape of parsed rows, and where data is filtered along the way.

Code lives in app/core/: parser.py (extract parsing), processor.py (fixed-width reports), loader.py (SQLite), common.py (week indices).

Model assumptions

The week is the smallest unit of time. A week of actuals counts as complete only when every one of its days is present. Until then it is held back and is not available to train on.

Weeks are ISO weeks. Each is stored as one integer index: the number of whole weeks since Monday 2000-01-03, which is ISO 2000-W01. Consecutive weeks always differ by exactly 1, including in 53-week ISO years such as 2026, so lags like orderidx - 4 are safe. Use week_to_idx / idx_to_week in common.py to convert. Don't compute an index by hand. The Load and Train page scripts mirror these functions.

The ISO year is used rather than the calendar year, so that a date such as 12/31 stays in the same week as the rest of its week.

  • orderidx: the week a quantity is demanded or consumed.
  • predidx: the week a forecast was released.

The prediction dataset holds one row per unique (part, orderidx, predidx) triple. Each part therefore has one forecast quantity per order week, per release, per plant.

Ingestion formats

Each plant has a source-system key (AT, CU3, 485, …). Weekly extracts are named {key}_custdemand.txt and {key}_ictrans.txt. Older history arrives as fixed-width YYYYwkWW.prn reports. Both kinds can be loaded by hand on the Load page.

Customer demand: {key}_custdemand.txt

Pipe-delimited, with fixed header columns followed by one column per forecast week:

Ship-From|Description|Order|Line|Customer|Customer Sort|Ship-To|Name|Week#|Rel Date|SO|Ln|ShipTo|Customer Part|Part|PCR|00/00/00|...

Each MM/DD/YY column is an order week, and its cell is the quantity forecast for that week in the release dated Rel Date. custDemandParse melts these columns into rows (orderdate, predqty).

Ship-From|Description|Order|Line|Customer|Customer Sort|Ship-To|Name|Week#|Rel Date|SO|Ln|ShipTo|Customer Part|Part|PCR|08/03/26|08/10/26|08/17/26|08/24/26|08/31/26|09/07/26|...
AT00|IAC Group - Arlington|GMA139|8|01008607|DAKKOTA INTEGRATED SYSTEMS|01009399|INTIER-KELLER ROAD WAREHOUSE|32|08/03/26|GMA139|8|01009399|84824532|84824532|6|0|0|0|1|0|0|...
AT00|IAC Group - Arlington|GMA139|29|01008607|DAKKOTA INTEGRATED SYSTEMS|01009399|INTIER-KELLER ROAD WAREHOUSE|32|08/03/26|GMA139|29|01009399|84824550|84824550|26|0|0|1|0|1|1|...

Transactions: {key}_ictrans.txt

Pipe-delimited inventory transactions. Only ISS-SO rows (issues to sales orders) are kept as consumption. Other types, such as ISS-WO below, are dropped.

Plant database schema

Each plant gets its own SQLite file at data/processed/{plant}.db, created by sql_setup() in app/core/loader.py. All plants share the six tables below. These files are what Backups protects.

No foreign keys

Tables relate only through part and the week indices orderidx and predidx. SQLite enforces none of these links, so a part can exist in one table and be missing from another. filter_disjoint() trims those parts at dataset time.

loaded_files is per week

Its key is (data_type, week_idx), not the filename. A waterfall extract writes one row per release week it covers, and a consumption load writes one per closed order week. The loaders read it back to skip weeks that are already closed. cost loads are not logged.

Schema version

sql_setup() runs migrate_schema(), which upgrades older databases in place. Version 1 moved the old pre-aggregated consumption into consumption_agg. Version 2 re-encoded every week index from year * 52 + week to weeks since 2000-01-03. It dropped rows stored at old index 105405, where 2026-W53 and 2027-W01 had been merged.

Parsed row formats

Both waterfall sources (the demand extract and the legacy diamond report) pass through waterfallProcess in parser.py. That function lower-cases and normalises column names, computes the week indices and keeps only the columns in WATERFALL_KEEP. These are the columns of the waterfall landing table:

ColumnMeaning
partPart number, cast to str and stripped.
reldateRelease date of the forecast.
shiptoShip-to location. One part can be forecast separately for several destinations.
pcrPCR value from the source, as an integer.
predqtyForecast quantity for the order week, from the melted date columns. Stored as qty in the landing table.
predidxWeek index of the release: ISO year/week of reldate.

Week#, SO, Ln, CustomerPart, orderdate and the intermediate lookahead/year/week columns are dropped once the indices exist. The result is deduplicated. Landing rows are unique on (part, orderidx, reldate, shipto). waterfall_agg then sums across ship-tos to the (part, orderidx, predidx) triple the models use.

The other parsers produce simpler shapes from the same fixed-width reader. The consumption shapes are in Transactions and Legacy .prn reports, and the cost shape is in Cost / price lists.

Filtering

Data is filtered at several points, each for a different reason. Rows that are clearly not useful (wrong transaction type, malformed part numbers, page furniture from reports) are dropped before SQL ingestion. Everything else is kept at full extent in the database, because features such as rolling values need the full history. Narrowing to a modelling set happens later, at dataset time.

Areas for future improvement

Alternative cost functions
Currently, the objective function can be chosen between minimizing error (number of units difference between predicted and actual orders).
  • Higher short-supply penalties: Punish the model much more if it underpredicts stock. This will encourage the model to take fewer risks.
  • Part-specific weights: Weight the part numbers such that the most important parts (e.g. by cost or volume) are the most impactful to the model. Error is currently concentrated: a small number of parts (~50) carries most (~60%) of the error.
  • New metrics for error reporting: Mean absolute error and mean squared error consider undershoot/overshoot equivalent. While weighting and penalties will just make the impact of certain parts/undershoot result in a larger MAE for the same amount of error, it might also be useful to look at this in terms of each metric individually.
Resiliency against incomplete data
The current model updates on a week-by-week basis; we chose this because although data is updated daily, predictions are made per location while ordering is aggregate, making validation per prediction impossible. However, this requires us to wait until all possible week data is known prior to making new predictions or validating old ones.
Plant-to-plant model transferability
The current model requires part numbers to be distinct to work; duplicated part numbers result in misattributed demand/ordering. While using internal part numbers might enable data to be aggregated, consideration should be given as to the value of insight relating to this.
Dynamic cost
When cost data was delivered, I was instructed to only use the latest cost. However, registering costs to the date of the prediction/forecast may be important, I'm not sure.
Improved augmentation strategies
The current approach uses either last value or prior-year order to project a forward customer order. While this is not the only feature used for these forward projections, these choices can be pretty impactful the further in the future projections are made. For example, for the "last value" strategy, a PN which is otherwise only ordered every other week might end up with a multi-week forecast of zero or double stock.
Broader hyperparameter search
app/optimize.py samples a fixed search space at random. Future work could expand the parameter sets and use a smarter search (e.g. Bayesian or gradient-based).
